def highlight(text: str, sources: list[str]) -> str:
    text_list = text.split(" ")
    text_coord = []
    positions = {}                                   # word -> every index where it occurs
    for i, word in enumerate(text_list):
        positions.setdefault(word, []).append(i)
    for source in sources:
        source_list = source.split(" ")
        source_len = len(source_list)
        for start_index in positions.get(source_list[0], []):     # only where the first word occurs
            if source_list == text_list[start_index: start_index + source_len]:
                text_coord.append((start_index, start_index + source_len))   # half-open [a, b)
    text_coord.sort()

    merged_coord = []                                # LC 56; half-open, so overlap is strict <
    for left, right in text_coord:
        if merged_coord and left < merged_coord[-1][1]:
            merged_coord[-1] = (merged_coord[-1][0], max(merged_coord[-1][1], right))
        else:
            merged_coord.append((left, right))

    res = []
    cur = 0
    for left, right in merged_coord:
        res.extend(text_list[cur: left])             # untouched words before the region
        res.append("<hl>" + " ".join(text_list[left: right]) + "</hl>")   # one piece per region
        cur = right
    res.extend(text_list[cur:])
    return " ".join(res)
Lineage & follow-ups — what this problem is made of, what to do before and after it

What it is asking. A model wrote text; sources are passages it may have copied from. Mark every stretch of the answer that appears word-for-word in a source, so a reader can see which claims are grounded. The pipeline has four steps and no new algorithm: split text into a word list; for each source, find every position where the next len(source) words equal the source's words (one source can match many times — don't stop at the first); collect all matches as word-index intervals; sort by start, merge the overlapping ones (LC 56), and rebuild the string with a tag around each merged interval. The spec hides three rules, and each test group checks one: whole-word only (aa never matches inside aaab), overlapping matches become one region (transitively — A touches B, B touches C, so A-B-C is one region even if A and C don't touch), and regions that merely sit next to each other stay separate.

Parts on the map. 2 pointers / walk: the match test is words[i:i+m] == source_words slid along the text. Segment / Interval and Sort: the merge is exactly 56 — sorting is what makes the single greedy pass legal, because once an interval's start is past the current region's end, every later interval starts even later and can never reach back. Hashmap and Trie are how you stop the naive scan from being n·L (next paragraph). Set would be the wrong tool here: it answers "is this word present", the question is "do these m consecutive words appear in order".

Why the limits are what they are. 1e5 characters is about 20,000 words; 2,000 sources of a few words each is a few thousand words of patterns; the naive per-source scan is words × pattern-words, around 1e8 comparisons — the local harness clocks it at ~2 s, and the limits were chosen to punish exactly that. The ladder: (1) index the text once, word → its positions, and only test a source at the positions where its first word occurs; (2) put all sources in a trie over words and scan the text once, walking the trie from each position — every position costs at most the longest source, and this is 212 Word Search II's pruning on a one-dimensional grid; (3) rolling hash over word windows (Rabin–Karp); (4) Aho–Corasick, KMP for many patterns at once, one pass over the text, the textbook optimum — name it, write the trie. A free consequence of (2): matches come out in left-to-right order, so the sort disappears and the merge runs as you scan.

class Spreadsheet:
    """Parts 1-3 the way a first sitting writes them. Values are computed at set time, so get is one lookup.
    Part 1: store + look up. Part 2: _value (recursive) and the recompute loop in set_cell.
    Part 3: the while loop at the top of set_cell, and delete_cell."""

    def __init__(self):
        self.formulas = {}                           # label -> raw string: "10" or "=A1+5"
        self.values = {}                             # label -> int | None, rebuilt on every set

    def set_cell(self, cell, expression):
        if expression.startswith("="):               # part 3: walk the new formula's references; reaching cell = cycle
            stack = [t for t in expression[1:].split("+") if not t.isdigit()]
            seen = set()
            while stack:
                cur = stack.pop()
                if cur == cell:
                    return False
                if cur in seen:
                    continue
                seen.add(cur)
                raw = self.formulas.get(cur, "")
                if raw.startswith("="):
                    stack.extend(t for t in raw[1:].split("+") if not t.isdigit())
        self.formulas[cell] = expression             # part 1
        self.values = {}                             # part 2: recompute everything now, so get stays a lookup
        for c in self.formulas:
            self._value(c)
        return True

    def get_cell(self, cell):
        return self.values.get(cell)                 # one lookup

    def _value(self, cell):
        # part 2: the value of one cell; references are computed first by recursing; results land in self.values
        if cell in self.values:
            return self.values[cell]
        raw = self.formulas.get(cell)
        if raw is None:                              # unset
            v = None
        elif not raw.startswith("="):
            v = int(raw)
        else:
            v = 0
            for t in raw[1:].split("+"):
                x = int(t) if t.isdigit() else self._value(t)
                if x is None:
                    v = None
                    break
                v += x
        self.values[cell] = v
        return v

    def delete_cell(self, cell):
        self.formulas.pop(cell, None)
        self.values = {}
        for c in self.formulas:
            self._value(c)

class SpreadSheet:
    def __init__(self):
        self.cell_value_map = {}
        self.cell_formula_map = {}

    def get_cell(self, cell):
        return self.cell_value_map.get(cell, None)

    def convert_expressions(self, expression):
        # convert an expression string into list
        items = []
        if expression.startswith("="):
            #items.append("=")
            for p in expression[1:].split("+"):
                if p.isdigit():
                    items.append(int(p))
                else:
                    items.append(p)
        else:
            items = [int(expression)]
        return items

    def set_cell(self, cell, expression):
        items = self.convert_expressions(expression)
        if self.detect_cycle(cell, items):
            return False
        self.cell_formula_map[cell] = items
        self.recompute_all()
        return True

    def recompute_all(self):
        self.cell_value_map = {}
        for cell in self.cell_formula_map:
            self.evaluate(cell)

    def evaluate(self, start):
        # mental model:
        # compute A1
        # A1:[B1, C1, D1, 1]
        # B1:[C2]
        # C1:[5]
        # D1:[NONE]
        stack = [start]
        while stack:
            cell = stack[-1]
            if cell in self.cell_value_map:
                stack.pop()
                continue
            if cell not in self.cell_formula_map:
                self.cell_value_map[cell] = None
                stack.pop()
                continue
            unresolved_reference = False
            for t in self.cell_formula_map[cell]:
                if isinstance(t, str) and t not in self.cell_value_map:
                    stack.append(t)
                    unresolved_reference = True
            if unresolved_reference:
                continue
            total = 0
            for t in self.cell_formula_map[cell]:
                v = t if isinstance(t, int) else self.cell_value_map[t]
                if v is None:
                    total = None
                    break
                total += v
            self.cell_value_map[cell] = total
            stack.pop()

    def detect_cycle(self, cell, items):
        stack = [t for t in items if isinstance(t, str)]
        seen = set()
        while stack:
            cur = stack.pop()
            if cur == cell:
                return True
            if cur in seen: #A1 = B1 + C1; C1 = D1 AND B1 = D1, D1 appear twice, but only need to appear once
                continue
            seen.add(cur)
            for t in self.cell_formula_map.get(cur,[]):
                if isinstance(t, str):
                    stack.append(t)
        return False

        self.cell_formula_map.pop(cell, None)
        self.recompute_all()

        # iterative post-order: a cell is computed only after every label it
        # references is in memo; memo is per-GET so edits are always visible
        memo = {}

def list_files(root, fs):
    # explicit queue instead of recursion (BFS; a stack here would be DFS, same answer, different memory shape).
    # visited is keyed by fs.identity, not by path: a symlink makes one directory appear under a second path.
    files = []
    seen_dirs = set()
    seen_files = set()
    queue = deque([root])
    while queue:
        d = queue.popleft()
        try:
            ident = fs.identity(d)
            if ident in seen_dirs:
                continue
            seen_dirs.add(ident)
            children = fs.list_dir(d)
        except OSError:
            continue
        for p in children:
            if fs.is_dir(p):
                queue.append(p)
                continue
            try:
                ident = fs.identity(p)
            except OSError:                             # dangling symlink etc.
                continue
            if ident not in seen_files:                 # the same file reachable by two paths: once
                seen_files.add(ident)
                files.append(p)
    return files

Follow-up ① — searching a real filesystem: DFS or BFS? (a short story)

So — DFS or BFS? Honestly, either one visits every node exactly once. The more interesting question is what happens when you point a walker at a real disk. For the record: classic single-threaded tools like find and Python's os.walk run iterative DFS; modern parallel ones like fd and ripgrep run a work queue that's BFS-shaped. And note the filesystem itself doesn't search anything — all it gives you is readdir. Searching is the tool's job.

Say you write the obvious thing first: a recursive function — read a folder, recurse into each subfolder. The call stack can break. Recursion spends a resource you don't control: Python gives you about a thousand frames before RecursionError; a C thread gets ~8MB of stack, then a segfault. Practically, nobody nests folders a thousand deep — and you'd be right, human-made trees are shallow. Which is exactly the clue: when a walker dies of "depth" in the wild, it's almost never depth. It's a cycle wearing depth as a costume.

Where would a cycle even come from? mkdir can't make one — every directory has exactly one parent, so the tree really is a tree. The culprit is symlinks. One line — ln -s / /home/me/loop — and your walker strolls into /home/me/loop/home/me/loop/… forever. Here's the nasty part: every lap produces a brand-new path string, so a visited set keyed by path never fires. Paths are nicknames, and a file can have many. What it has exactly one of is its inode — the metadata record the filesystem keeps for it. Inode numbers repeat across disks, though, so the real identity is the pair (st_dev, st_ino), both straight out of os.stat(). Same move as cycle detection in any graph problem: mark the node, not the route you took to reach it.

So the fix for the crash isn't "raise the recursion limit" — that's a band-aid (Python at least fails loudly; C just dies). The fix is to keep the exact same DFS order but move the to-do list somewhere you own: an explicit stack, literally a Python list with append and pop. The difference is real estate — the call stack is megabytes, your heap is gigabytes, and the failure mode becomes a clean OOM instead of a crash. If you've ever rewritten recursive inorder traversal into the iterative version (LC 94), you've already made this exact move. The standard library agrees, by the way: os.walk is implemented iteratively.

Now the parallel story. You want ten-plus workers on this, and recursion is awkward to parallelize because each thread's frontier is buried in its own call stack — private by construction. So you turn the frontier inside out: one thread-safe queue holding folders-to-visit, seeded with the root, and a fixed pool of workers, each looping grab a folder → readdir → handle the files → push the child folders back. Notice what happened to "levels": they dissolved. Nobody waits for level three to finish before touching level four; this is BFS-shaped only in the sense that the frontier is a shared queue.

Three details separate this from a toy. Worker count follows the bottleneck, and the bottleneck is disk IO, not CPU — 8 to 32 threads saturate an SSD, so a million folders means a longer queue, not a bigger pool (fd defaults to one thread per core). Termination is the subtle bug: an empty queue does not mean you're done — some worker may be mid-readdir, about to push ten more folders — so you track in-flight work with queue.join() + task_done(), or an atomic counter. And the visited set is shared now, so lock it or shard it — still keyed by (device, inode).

One last thing. If you search the same disk often, the grown-up answer is to stop traversing altogether: crawl once, build an index, query the index — which is exactly what Spotlight and Windows Search do. Traversal is for cold, one-shot scans.

Follow-up ② — the files are gigabytes now (a funnel story)

In the toy version, the dict key was the file content itself. With gigabyte files that dies twice: memory — every unique content sits in the dict as a key — and time, because you read every byte of every file even when nothing matches anything. First instinct: key by hash(content) instead. That fixes memory — 32 bytes per file. It does nothing for IO: to hash a file you still read all of it, and a terabyte at 500MB/s is a good half hour of pure reading. So the real question isn't "how do I compare big files" — it's how do I avoid reading most bytes at all?

The observation that unlocks it: duplicates are rare. Most files don't need an exact fingerprint — they need a cheap proof of innocence. And proving "this file has no twin" is far cheaper than proving "these two are identical": a unique file size is already a full acquittal, and size is free. So run cheap eliminations first and spend real reads only on survivors. A funnel.

Stage one: group by size, straight from stat() — zero content IO. Same content implies same size, so a unique size exits immediately; on a typical disk that's most files gone for free. Stage two: within a same-size group, hash a sample — the first 4KB and the last 4KB. Both ends, because same-format files share headers (every MP4 opens alike, log files share their first lines), so prefixes collide innocently; tails split the append-heavy cases. One disk page instead of the whole file. Stage three: whoever still has company gets fully read — in chunks, a megabyte at a time, fed into a streaming SHA-256; memory stays constant no matter the size, and the digest becomes the group key. (How a 32-byte state eats a terabyte file is a story for another post.) Stage four is optional and business-shaped: if the next step deletes files, or a wrong match is a lawsuit, compare survivors byte by byte, bailing at the first mismatch — almost nothing reaches this stage, so it's cheap.

Now, which stage answers for which mistake? Think of the middle stages as pulling suspects and only the last stage as convicting. A real duplicate can never escape early: every stage keys on a function of the content — same content forces same size, same sample, same digest — so true twins ride the funnel together to the end, structurally. Meanwhile the middle stages wrongly suspect innocent files all day (same size, different content — happens constantly), but a wrong suspicion costs a few extra kilobytes of reading, never a wrong answer, because grouping isn't a verdict. The false-positive rate of the whole pipeline is set by exactly one thing: the strictness of the final stage. Trust SHA-256's ~2⁻¹²⁸ for a report; add the byte-compare when the output deletes things.

What did we buy? Total IO drops from "read everything" to: one metadata pass, plus 4KB per same-size file, plus full reads only for near-twins. The worst case — a disk full of same-size, same-header files — degenerates back to hashing everything; adversarial inputs exist, real disks aren't. And stage three parallelizes with the same worker queue as the traversal story, because this whole business is IO-bound.

Once you see the shape you see it everywhere: size-then-sample-then-hash-then-bytes here; a bloom filter in front of the disk lookup in LSM stores; cheap embedding recall in front of an expensive reranker in retrieval pipelines. Even hashing itself comes in cheap and expensive tiers — dedup tools run xxHash or BLAKE3 in the filter stages and save the cryptographic hash for verdicts. Cheap proxies first; the exact check only for survivors.

import heapq
import math


def cosine(a: list[float], b: list[float]) -> float:
    dot_product = sum(a[i] * b[i] for i in range(len(a)))
    a_length = math.sqrt(sum(a[i] * a[i] for i in range(len(a))))
    b_length = math.sqrt(sum(b[i] * b[i] for i in range(len(b))))
    if a_length == 0 or b_length == 0:
        return 0.0                       # convention: a zero vector has no direction
    return dot_product / (a_length * b_length)


def top_k(query: list[float], docs: list[list[float]], k: int) -> list[int]:
    res = []
    for index, doc in enumerate(docs):
        sim_score = cosine(query, doc)
        heapq.heappush(res, (-sim_score, index))   # min-heap: negate so the best pops first;
    output = []                                    # equal scores fall through to the smaller index
    for i in range(min(k, len(docs))):             # also covers k == 0 and k > len(docs)
        output.append(heapq.heappop(res)[1])
    return output


def precision_recall_at_k(retrieved: list[int], relevant: set[int], k: int) -> tuple[float, float]:
    correct = relevant.intersection(retrieved[:k])          # only the first k count
    precision = len(correct) / k if k else 0.0              # of what I showed, how much was right
    recall = len(correct) / len(relevant) if relevant else 0.0   # of what was right, how much I showed
    return (precision, recall)


def evaluate_retrieval(query, docs, relevant, k) -> tuple[float, float]:
    return precision_recall_at_k(top_k(query, docs, k), relevant, k)

Parts on the map. Heap does the ranking, and there are two ways to hold it. Push every doc and pop k times — heap of size n, n log n, no better than sorting, but easy to get right: store (-sim, index) so the best score is the smallest tuple and equal scores fall through to the smaller index. Or keep only the k best — heap of size k, n log k: now the root must be the worst of the k, so store (sim, -index) un-negated, push while the heap is short, otherwise compare with heap[0] and heapreplace, and sort the survivors at the end. Same tie rule, opposite encoding, because one design wants the best on top and the other wants the worst on top. Set counts the hits: relevant.intersection(retrieved[:k]) — a list has no intersection because answering "is x in there" costs a scan; a set answers it with one hash. Follow-up spoken answer — scaling retrieval: FAISS and vector databases (a short story)

So the brute-force version costs n times d multiplications per query. One million documents at 1,536 dimensions is 1.5 billion multiplications — a few hundred milliseconds on a CPU. That's fine at ten thousand documents and hopeless at ten million. FAISS calls the brute-force version a Flat index, and it's the right answer more often than people admit: exact, nothing to tune, and on a GPU it stays fast into the millions. Past that you accept approximate answers, and the whole game becomes measuring how approximate — which is exactly recall@k from part 3, with the Flat index's answer standing in as the relevant set.

Three ideas, in the order people usually stack them. IVF: run k-means over the corpus into, say, 4,096 clusters and remember each center. At query time compare the query to the 4,096 centers (cheap), pick the closest few — nprobe, say 8 — and scan only those clusters. The work drops by roughly 4,096 over 8. The miss case is a true neighbor sitting just across a boundary in a cluster you didn't probe; raising nprobe buys recall with time. PQ: shrink the vectors so the scan is cheaper and the index fits in RAM. Cut 1,536 dimensions into 96 chunks of 16; for each chunk learn 256 representative sub-vectors; store each chunk as the one-byte id of its nearest representative. 6,144 bytes become 96, and distance to a query is a table lookup per chunk. The loss is quantization error. IVF plus PQ is the classic recipe for a billion vectors on one machine. HNSW: no clusters, a graph. Every vector links to a few near neighbors, and the graph is layered like a skip list — the top layer holds a handful of points with long-range links, the bottom holds everything. Search enters at the top, hops greedily to whichever neighbor is closest to the query, and drops a layer when it can't improve: a logarithmic number of hops instead of a scan. Best recall-for-speed when the data fits in memory; the price is memory for the edges and slower inserts.

Vector databases — Milvus, Qdrant, Weaviate, Pinecone, Chroma, pgvector, Elasticsearch's kNN — all run these same two or three algorithms inside. What they add is the database part: filtering by metadata next to the vector search (harder than it sounds — filter first and you break the index's assumptions, filter last and you may be left with too few results), keeping the index fresh as documents change, and sharding across machines. If you already run Postgres, pgvector is the no-drama place to start.

And the metric closes the loop. Run the exact search once to get the truth, then measure the approximate index's recall@k while turning nprobe or ef up until recall clears your bar. That knob is the whole tuning story, and the number you report is a sentence like "recall@10 of 0.97 at two milliseconds."

Variants seen in the same pool: versioned KV store with consistency checks, DB connection pool (concurrency), file system with capacity limits — same shape; recognition is enough.

№1 · Hashing Algorithms — 从 hashmap 的发动机到 SHA-256 的最后一行加法

它是什么。hash 函数就是一个普通函数:输入随便多长,输出固定这么长(SHA-256 是 32 字节)。它的所有用途都从"输出固定且短"这一条长出来:短,才能当数组下标;短,才能当身份证;短,才能贴在文件旁边当印章。要是指纹和人一样大,按指纹就没有意义了——直接比人就行了。

用途一:当地址——这是它和 hashmap 的关系。数组是最快的容器,但数组只认下标:你给它 3,它一步到位;你给它 "apple",它不认识。key 不是下标,所以想让 key 享受数组的速度,就必须有人把 key 翻译成下标。hash 就是这个翻译员:下标 = hash(key) mod 桶数。翻译要满足两条,每条都是常识:第一,同一个 key 每次翻译结果必须一样——不然存的时候放进 3 号桶,取的时候被翻译成 7 号,东西就丢了;第二,不同 key 要尽量落进不同的桶——大家都挤 3 号桶的话,桶里就得排队挨个找,O(1) 退化成 O(n)。所以 hashmap = hash(负责翻译)+ 数组(负责兑现)。图上的 hmap 和 Set 两个节点,装的都是这台发动机。

用途二:当指纹——这是它和 609、git 的关系。两个 1GB 的文件想知道是否相同,逐字节比要读 2GB;先各算指纹,指纹只有 32 字节,比指纹是一瞬间的事。这里的逻辑必须拆成两个方向,因为两个方向的可靠程度不一样。内容相同 → 指纹一定相同:这是"函数"两个字自带的,同样的输入进同一个函数,出来必须一样。指纹相同 → 内容只是"几乎一定"相同:输入有无穷多种,输出只有 2²⁵⁶ 种,格子有限、鸽子无限,必有不同的输入共用同一个指纹——只是 2²⁵⁶ 个格子实在太多,随机撞上的概率小到天文数字分之一。前一个方向是铁的,后一个方向是概率的。去重漏斗的合法性就建立在铁的那个方向上:真重复的两个文件在每一层都必然同组,永远不会被中途放走;概率的那个方向决定的只是最后一层要不要再逐字节确认。

用途三:当印章——这是它和密码、签名的关系。前两个用途的敌人是运气(碰巧撞上),这个用途的敌人是人(有人故意想撞)。网站不存密码原文,存 hash(密码):数据库被偷,贼拿到的只是指纹,倒推不出密码。这就对 hash 提出了新要求:不能倒推、不能故意造碰撞。能同时满足的,才配叫加密 hash。

它在图上的位置。hashing 自己不是节点——图上的节点是能练的结构和走法,hashing 是藏在节点里的发动机,就像"比较"藏在 Sort 里,你不会给"比较"单独建一个节点。它点火的节点:hmap 和 Set(地址用途)、LRU(焊接的一半)、560 那种拿前缀和当 key 的用法(指纹用途的变体)。它的对手是 TreeMap/BST/B+:同样做"按 key 找东西"的生意,hash 把 key 打散,换来 O(1) 点查,代价是顺序信息全毁;有序家族把 key 排好,O(log n),换来邻居、区间、第 k。选哪边就问一句:以后要不要问邻居、区间、第 k?要,去有序家族;永远只问"有没有、是多少",用 hash。它和 BIT 没有关系——BIT 做的是按下标聚合,另一门生意,不用硬连。唯一以"算法"身份能上手练的形态是 rolling hash(187 / 1044):窗口挪一格,指纹 O(1) 更新——hash 和滑窗的焊接。

SHA-256 内部:三个变量,一个循环。台上只有三样东西:state(8 个 32-bit 整数,初始值是固定常数)、block(你的输入切成的 64 字节段)、K(64 个写死的常数)。主流程就是一个 for 循环:每圈拿 state 和一个 block 进 compress,出来新的 state;所有 block 处理完,把 8 个整数拼成十六进制,就是指纹。"能处理任意大的文件"没有任何魔法——循环多转几圈而已,手里永远只有 8 个整数加当前的 64 字节,所以内存恒定,1TB 的文件照样是这 8 个整数。hashlib 的 update(chunk) 就是往这个循环续料,state 在两次 update 之间接着用。

compress 里面,你的输入只有一个入口。进来的 64 字节先按 4 字节一切,变成 16 个整数 w[0..15]——原样,一个字节没动;然后递推生成 w[16..63],每个新词由四个旧词加一加、转一转得到。为什么要从 16 个扩展成 64 个:一是后面有 64 轮、每轮要消费一个词;二是递推让后面的每个词都掺进了多个原始词——改输入的一个字节,不是只影响某一轮,是污染后面几十轮的原料。正式的 64 轮里,每轮算一次 T1 = h + S1(e) + Ch(e,f,g) + K[t] + w[t]:这串加数里只有 w[t] 是你的数据,其余全是在搅已有的 state。你的输入就从这里、每轮一个词、分 64 次进场——这是它唯一的入口。

单向性来自最后一行,不来自那 64 轮。64 轮转完得到 8 个工作变量,函数最后做的事是:new[i] = old[i] + working[i],把轮前的 state 逐个加回轮后的结果。这一行是命门,因为那 64 轮每一轮其实都可逆——知道轮后的值就能一步步倒回轮前。假如没有这行,拿到输出就能反着走回输入,hash 就白设计了。加了这行,输出变成 new = old + f(old, block):你手里只有 new,想解出 block 得先知道 old,而 old 正是另一个未知数。一个方程,两个未知数,解不动——单向性就是这一行加法买来的。

为什么轮里偏偏是那三种操作。加法、旋转+XOR、Ch/Maj,各管一条路。加法有进位,低位的变化顺着进位往高位爬——纵向扩散。旋转把每一位搬到别的位置,XOR 把三个搬运结果叠在一起——横向扩散。Ch 和 Maj 的本质是 AND:如果整个函数只有加法和 XOR,它就是线性的,而线性方程组是可以解的;有 AND 在,方程组解不动——这是非线性的来源。三样凑齐,64 轮转完,输入动一位,输出大约翻一半,这就是雪崩。

家族全景:按你怕什么分档。什么都不怕、只要快:xxHash、Murmur——去重漏斗的过滤层、分片路由,能跑到内存带宽的速度(每秒几十 GB);过滤层允许误报,判决另有人做,所以这里用最快的。怕有人捣乱你的 hashmap:SipHash。这种攻击真实存在:有人算好一批全部落进同一个桶的 key 发给你的服务,你的 dict 每次操作都变成排长队,服务就瘫了,这叫 HashDoS。SipHash 带一把随机钥匙,攻击者不知道钥匙就算不出哪些 key 会撞。Python、Rust、Ruby 的内建 dict 都用它——顺便解释一个现象:Python 每次重启,hash("a") 的值都不一样,因为钥匙是进程启动时随机发的。怕有人故意造碰撞:必须加密档。MD5(1992)在 2004 年被攻破——注意"攻破"的意思不是"容易随机撞上"(随机撞的概率仍然小到天文数字分之一),而是"有人能故意造出两个内容不同、指纹相同的文件"。SHA-1 在 2017 年同样倒下,git 因此搬家。现役是 SHA-256(新 CPU 带硬件指令,常常反而比 MD5 快)和 BLAKE3(又快又防,还能切块并行)。怕别人猜你的密码:Argon2、bcrypt——这一档故意慢,和其他所有档方向相反。道理是常识级的:你自己登录,一秒算一次,无所谓;贼拿了库暴力试密码,恨不得一秒试十亿次——hash 越快,帮的越是贼。所以密码 hash 故意烧时间烧内存,把贼的成本抬上天;拿裸 SHA-256 存密码不是"不够安全",是方向本身就反了。最后是家族里的叛徒:MinHash 和 SimHash。正常 hash 的美德是"差一位,天翻地覆";这两个反着来,内容越像、指纹越像,专做"近似重复"的检测——LLM 训练语料的去重就是先精确 hash 去一遍,再 MinHash 去相似的。

MD5 的判词。防事故够用,防对手不行;而今天,论快有 xxHash,论安全有 SHA-256 和 BLAKE3——两头都被占了,MD5 没有剩下的位置。面试里被问到,答案就是这一句加上前面那对定义:事故 = 碰巧撞上,对手 = 故意造撞。

  • "镜像"指哪一层：两层。ADK 这个库的源码有内部镜像（不能随便 checkout 外部 GitHub）；模型调用走公司统一的内部 API，一个壳后面是几家的模型，所以数据不出域、换模型改一个名字。
  • tracing 看什么：这是 agent，每一轮——对话也好、tool call 也好——都要记下来，哪里答错、哪个工具调得不好，后面复盘和改 prompt 全靠这个；另外内部模型 API 不稳定，有时候莫名其妙不好用，trace 里有 input/output 和每次调用的起止时间，才查得出是哪一段出了问题。
  • 换模型怎么知道没坏：照实说——这不是固定 workflow，是交互式的，换模型确实可能把原来好的弄坏，用户不仔细也可能漏过。做法是让模型先做 atomic 的任务，保证简单问题不出错；但简单题对推不出复杂题对；反过来也不成立——这是我们 review 别的 team 的模型时让他们的 developer 做 atomic 测试、对方 pushback 出来的：线索多了模型会自己 cross validate，复杂任务里 context 更全，有时反而避开简单题里的错。所以 atomic 回归是必要条件不是充分条件，两头都得看。固定几十上百个 golden case 随时跑，只对输出短而固定的系统管用（一个词、一句话）；输出是一段分析加一张图，不好这么量。
  • 为什么 Vespa：公司现有栈；这块实习生做的，我 oversee 的是她试不同 chunking strategy 那一段。检索只有向量一路（cosine），没做 BM25；后面接一个 cross encoder 做 rerank。被问"专有名词在向量里被抹平怎么办"时照实答：知道该加一路字面匹配，没加；专有名词这类需求现在是靠另一个 tool 顶的（下面 MCP 那条）。
  • chunking 试了哪几种：按字数、按段落、按文档结构、带重叠，四种都做了。被问"哪种赢了"时别报一个赢家：文档本身不是一类——有的全是公式，有的全是 regulatory requirement，同一种切法在两类上表现不一样；而且金融数学的知识点是网状的，一个知识点牵着好几个文档里的好几段，指望一种 chunking 把这事解决掉本来就太简单了。真实结论是"按文档类型选切法，再往上要的是跨段落的关联，不是更好的切法"。
  • eval 怎么做：一份 questionnaire：按模型方向分五类（equity、rates、credit、treasury、credit risk），每类 10 题，每题五个选项的单选，问的是具体模型知识（比如 equity 的某种 local vol 能用哪些模型、怎么建）；同一套题在每种 chunking 下各答一遍，每类题找一位相关方向的同事打分。没有自动 judge，是人打分；没有多人交叉打分，因为能拉到人来 eval 已经是很大的 effort 了。
  • 并发：设计目标 50 个并发模型调用，async。

实际部署长什么样，被问细节时照实答。

  • 规模：K8s 上一个 pod；agent 进程、MCP server、MCP 里的 Python tool 都在这一个 pod 里，所以 MCP 之间不用额外鉴权。pod 前面没有 load balancer，所有请求进同一个 pod；pod 里一个 FastAPI backend 加一个前端，并发请求靠 FastAPI 自己的 async 队列排，没有定长队列。并发一高先撞的是模型 API 的 too many requests，server 端对模型调用做 exponential backoff，最多三次。另一个瓶颈是跑 Python 脚本的那个 MCP：脚本是和 agent server 平行的 Python 进程，跑在同一个 pod 里，多了会把 pod 的内存或 CPU 顶爆，现在的办法是最多同时跑两个。这正好对上 async 那条链的第 ⑤ 步：async 只救 IO 等待，CPU 密集的段要么限并发、要么进程池、要么加 pod。
  • 状态：会话状态在进程内存里，pod 重启正在聊的会话就没了。正确做法是会话落数据库、agent 无状态，知道但没做：一个人、没文档、没 support，team 的 mandate 本来也不是上线产品。
  • 延迟：一个表问题大约一分钟，六成以上时间花在公司的模型 API 上，因为 API 里带 guardrail，有一个模型在审用户问题和 agent 答案；API 不支持 streaming，所以用户看不到进度，这也是重试只敢 3 次的原因，第三次失败把 API 的 error 原样给用户。
  • 模型：公司网关每个 request 都能换模型，用户可以 hot switch；两家头部的差不多，没怎么换过。
  • 上下文：六轮以内全带，超过六轮让模型总结一遍留摘要。
  • 代码执行：模型写的 Python 在 server 里开新进程跑，三层隔离，每层挡一类风险。一、Python 开 isolated mode：只能 import 指定的包，不能从任意路径 import，挡的是"把坏代码藏进 module、import 时执行"。二、subprocess.run 的环境变量白名单：pod 里的用户名、密码、secret 不传进子进程，挡的是信息泄露。三、工作目录是临时目录，读写都在里面，进程结束整个目录删掉，挡的是和 pod 里别的文件混在一起。没有真沙箱（独立容器），知道该有，一个人做不过来。
  • MCP 里有什么：三类。一、model inventory 的 prebuilt query：固定好的几条查询，agent 不用现场 improvise——原因是这张表很多 column 是行内编码，agent 缺 context 容易误解，不如把常用查询写死。二、执行 Python 的 MCP（上面那条）。三、RAG 的 MCP 两个 tool：一个按 cosine 找相关段落塞回上下文，一个按关键词列出一整串模型。
  • 前端：React，能渲染 HTML 和图；React 不是我会的东西，是跟 AI 要出来的，面试里不讳言。
  • trace：每次调用写进 SQL 库：用户名、时间戳、输入、输出、tool 名、参数、起止时间；库跟着 pod 走，重启就没，没看板，known issue 没 bandwidth。
  • 检索规模：文档库上万份，embedding 了两三千份；embedding 模型换过（被禁那次）。
  • 用户：160 是 team 人数，活跃 10 到 20 人，内部工具的正常水平；登录走 SSO，允许名单是代码里的用户名列表，在网关拦：不在名单直接进不了应用，进来之后 model inventory 和模型调用都不再单独鉴权。merge 只有我能批。
  • 成本：token 账单看不到。

特例折进哪里：

  • 用户问的是一个数字 → 不是特例，是第 ④ 步"数字从代码出"的一般规则。
  • 模型把表格数字读错 → 同一条规则，表格走解析器不走模型。
  • 一个问题既要查表又要读文档 → 不是特例，agent loop 本来就是为"先查表再拿结果去检索"这种两步设计的。

Part 2 · 概念链（每条推一次，压成名字）

№1 · RAG：为什么必须有检索，检索的范围是什么

①要带出处的答案。②几千页文档 + 一个只认几万 token 的模型。③唯一办法：先选后读。④所以必须有检索。⑤范围：这个用户有权限看的文档。名字：RAG。

往下一层，每段同一个问法。切块：模型要的是能独立读懂的一段，文档给的是连续文本，唯一的运算是切，所以按结构切（标题、段落、表格整块）不按字数切，范围是"一块里的句子不被切断"，所以块之间留重叠。Embedding：检索要的是"像不像"，文本给的是字，唯一的运算是映射到向量再比距离，范围是"问题和文档落在同一个分布里"，所以问题和文档要用同一个模型编码。混合检索：专有名词（模型名、ticker、REQ 号）在向量里会被抹平，唯一补法是再加一路按字面匹配（BM25），两路取并集。我自己那套只有向量一路，这条是知道没做的。Rerank：粗检索便宜但不准，精打分准但贵，唯一的组合是粗选 top 50 再精排，范围是只对 top 50 做。

特例折进哪里：

  • 用户问的东西不在任何文档里 → 不是特例，折进 eval 的"该拒答"这一层。
  • 两个文档说法冲突 → 折进"答案带出处"，让用户看到两个出处。
№2 · Agent 与 tool calling：为什么下一步由模型定，范围由代码定

①要的是一个能回答"没预先写好流程"的问题的系统。②手里有模型、一组工具、用户的问题。③流程不能预写，所以下一步只能由模型按上一步的结果决定。④所以必须有一个循环：想 → 选工具 → 调 → 看结果 → 再想。⑤范围：模型只能选注册过的工具、只能传过校验的参数、只能走有限步数。名字：ReAct 式 agent。chain 和 agent 的差就在第③ 步：chain 的下一步是代码写死的。

MCP 是什么，同一个问法。①多个 agent 要用同一批工具。②每个工具的接口各写各的。③唯一的解法是统一接口协议。④所以有 MCP：服务端暴露 tools/resources/prompts，客户端按协议调。⑤范围：协议管接口，不管工具里面怎么实现。

多 agent 什么时候值得。只有当任务能按角色切开、每段有独立的工具集和 eval 时；否则一个 agent 加好工具更稳。这是"两个灵魂不硬合一"在系统上的版本。

HITL 放哪。不可逆动作（发邮件、下单、改数据）前；低置信度答案；新 workflow 上线头几周全量。

特例折进哪里：

  • 工具调用失败 → 不是特例，折进第 ⑤ 步的范围：返回结构化错误让模型重试，重试次数有上限。
  • 模型死循环 → 同一条，步数上限。
№3 · Eval：为什么要固定题集，hallucination 怎么量

①要知道"改了 prompt 或换了模型之后，变好还是变坏"。②手里有模型输出，但没有标准答案。③没有标准答案就没法比，所以唯一的办法是先造标准答案。④所以必须有 golden set：真实日志里抽问题，人工标答案和出处。⑤范围：题集要覆盖三类——简单事实、跨文档、该拒答的；只覆盖第一类的题集会把"什么都敢答"的模型评成最好。名字：固定题集回归。再加一句范围：固定题集只对输出短而固定的系统好使（分类、抽取、一句话答案）；输出是一段分析加一张图的交互式 agent，题集做不动，加上没有人力去标，退而求其次是 atomic 任务回归 + 看 trace 复盘，这是我实际做的。

hallucination 怎么量。①要知道答案里有没有编的。②手里有答案和检索到的出处。③唯一的运算：答案里每个事实能不能在出处里找到。④所以用 LLM-as-judge 逐条核对，人工抽查校准 judge。⑤范围：judge 只核对"有没有出处"，不核对"出处本身对不对"，后者是检索层的事。名字：faithfulness。

precision / recall 在 RAG 里各指什么。检索层：取回的块里相关的占比 / 相关块里取回的占比。答案层：说的对的占比 / 该说的说了多少。两层各一对，别混。

特例折进哪里：

  • judge 和人意见不一致 → 不是特例，折进"人工抽查校准 judge"，不一致率本身是一个指标。
№4 · prompt / RAG / fine-tune 怎么选，成本和延迟从哪来

①要模型按我的意思答。②手里有三个旋钮：改输入（prompt）、给资料（RAG）、改权重（fine-tune）。③每个旋钮只能改一类东西：prompt 改指令，RAG 改知识，fine-tune 改风格和格式。④所以按"要改的是什么"选：知识会变 → RAG；格式要稳 → fine-tune；都不是 → prompt。⑤范围：fine-tune 改不了知识（学完就过时），RAG 改不了风格。名字：三个旋钮各管一类。

延迟链。检索 50-200ms、rerank 100-300ms、首 token 500ms 起、之后按 token 计。流式输出改的是用户感受不是总时间。

prompt caching。①要省钱。②每次请求的前缀（系统提示、长文档）都一样。③一样的前缀模型侧算一次就够。④所以缓存前缀的 KV，只付增量。⑤范围：前缀必须逐字节一样，顺序变了缓存就失效，所以不变的放前面。

№5 · 系统基础：threads / processes / async，50 并发怎么扛（一家 multi-strat 问过）

①要同时服务 50 个人。②每个请求大部分时间在等模型 API 和检索返回。③等的时候 CPU 是闲的，所以唯一的浪费是"一个线程一个请求地干等"。④所以用 async：单线程里靠事件循环在等待时切换，一个 worker 挂几十个请求。⑤范围：只对 IO 等待有效；CPU 密集的段（embedding、解析大表格）要扔给进程池，因为 Python 的 GIL 让线程在 CPU 上不并行。名字：async worker + 进程池。我自己那套的真实情况：一个 pod，async 之后模型等待不是问题，先顶到头的是 MCP 里 Python tool 吃 CPU——所以第⑤ 步不是书上的话，是碰到过的。

threads vs processes，一句话。进程各自内存，崩了不连累、切换贵；线程共享内存，切换便宜、要锁。Python 多一条：GIL，所以 CPU 密集用进程。

扩容链。一个 worker 扛不住 → 多个 worker → K8s HPA 按队列长度扩 → 模型 API 有限流，所以 worker 再多也要在出口排队。幂等：模型调用可以重试，带副作用的工具调用要有 idempotency key。

可观测性。每次 agent 运行一个 trace，每步工具调用一个 span，记 token、延迟、成本。没有这个，eval 掉了都不知道是哪一步掉的。

№6 · AI-SDLC 和 governance（资管 AI 平台岗专项）

①要几千个开发者的代码生成、review、测试、迁移都用上 AI。②手里有模型和一堆各写各的团队。③每个用法的共同问题只有一个："怎么知道它没搞砸"。④所以每个用法配一个判决机制：生成的代码过现有测试 + 人 review；review 建议按历史 bug 校准；迁移用等价测试。⑤范围：判决机制必须是模型之外的东西（测试、人、历史数据），不能让模型自己判自己。名字：每个 AI 用法配一个外部判决。

怎么推到几千人。先给一个团队做样板，量 PR 周期和缺陷率，再做成平台能力：统一模型网关、统一 eval、统一审计。顺序不能反，先平台后样板会做出没人用的平台。

governance 的四问。模型看了什么数据、输出留痕了吗、谁能用什么工具、第三方模型的数据出域了吗。你 validation 的背景在这里是现成的答案。

buy vs build。模型买（自己训不过）、网关和 eval 自建（这是你的护城河）、agent 框架看公司栈。给一个你真做过的决定。

Part 3 · System design 模板（三条链，先问三件事：用户是谁、数据从哪来、答错了后果多大）

A · 给 PM 做一个读 SEC filings 的问答系统fund GenAI 平台岗

①PM 要"这家公司上季度 guidance 改了什么"，要出处，要当天。②EDGAR 上的 filings，表格多，同名公司多，财年口径乱。③模型读不完，先选后读 → RAG；数字在表格里，模型读表格会错 → 表格走解析器。④摄入（拉取 → 解析 → 按 item 切块 → embedding → 入库，增量更新）→ 检索（混合 + 按公司和日期过滤 + rerank）→ 生成（带出处）→ eval（题集 + 出处核对）。⑤范围：过滤的维度是公司 ID 不是公司名（同名），日期是 filing 日期不是财年。

只有两周先做哪两段：摄入和检索。生成可以先用最简单的 prompt，eval 先用 50 道题。

B · 后台持续跑的 agent，盯新闻、filings、邮件，给 PM 推摘要forward deployed AI 岗的 JD 原文

①PM 要"和我持仓相关的新东西"，不要重复，不要旧闻。②新闻 API、邮件、filings，量大、重复多、九成无关。③贵的判断（模型）不能对全量做，所以唯一的结构是便宜的在前、贵的在后。④事件源 → 去重（hash）→ 规则过滤（ticker、关键词）→ 相关性判断（模型，带持仓和关注列表）→ 摘要（带原文链接）→ 推送 → 反馈回流（点了没有，调阈值）。⑤范围：相关性的范围是"这个 PM 的持仓和关注列表"，不是全市场；去重的范围是"同一事件的不同报道"，不只是同一篇文章。

特例折进哪里：

  • 模型把旧新闻当新的 → 折进去重层，按事件而不是按文章去重。
  • 延迟 vs 成本 → 折进"便宜的在前"，调的是规则层的宽严。

C · 多团队共用的 LLM 网关和平台平台岗

①十几个团队都要用模型，各自要 RAG、要工具、要 eval。②每个团队自己接一遍，成本和风险都乘以团队数。③共同的部分只做一遍，唯一的办法是抽成平台。④统一入口（鉴权、配额、模型路由）→ 工具注册（MCP 风格）→ 检索服务（多租户，权限过滤）→ eval 服务（题集、judge、回归）→ 观测（trace、成本归属）→ 治理（审计、数据域）。⑤范围：平台管"共同的部分"，一个团队的 prompt 改动不能影响别人，所以 prompt 和工具按团队隔离，模型升级要灰度。

特例折进哪里：

  • 某个团队要用平台不支持的模型 → 折进"模型路由"，路由表加一行，不开后门。
